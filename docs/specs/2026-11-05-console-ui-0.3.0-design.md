# Console UI 0.3.0 design

> **Status:** DRAFT — the tower console moves from `@savvagent/console-ui@0.2.0` to `0.3.0`.
>
> **Implements:** savvagent/tower#300. **Part of:** savvagent/platform#154. **Builds on:**
> `docs/specs/2026-11-05-console-ui-shell-design.md` (#296), which wired the shell.

## Brief

Issue savvagent/tower#300. Bump `@savvagent/console-ui` to exactly `0.3.0` from GitHub Packages and
adopt what it changes, for the contrast and accessibility fixes in savvagent/console-ui#10, #12 and
#13. Acceptance criteria, from the issue:

- [ ] `npm run check`, `lint`, `test` and `build` pass, and so does the image build with the BuildKit
      secret.
- [ ] No `CardTitle` contains a nested heading, and every page's heading outline is unchanged.
- [ ] The footer's version is not a link.
- [ ] After release and deploy, `/healthz` and `/readyz` answer 200 and production shows the new
      destructive red and input borders.

## What 0.3.0 changes, and what tower does about each

| 0.3.0 change | Tower change |
| --- | --- |
| Destructive red raised to WCAG AA (console-ui#10); darker input borders and a full-strength destructive focus ring (#13). | None in code. The colours come from the shared tokens; the screenshot check confirms them. |
| Header triggers' accessible names start with their visible text (#13, WCAG 2.5.3). | None in code. No tower test asserts the old trigger names (checked: no `aria-label` assertion on a header trigger). |
| `OverwriteGetLocale` is `(fn: () => Locale) => void` (#12). | `bootLocale` calls `resolveAtBoot(overwriteGetLocale)`; the `as Locale` cast and the comment justifying it go. A runtime shipping fewer than six locales is now a type error, which is the guard the cast used to waive. |
| `CardTitle` takes `level?: 1–6` (#12). | Each of the nine `<CardTitle><h2>…</h2></CardTitle>` (overview ×2, job ×5, repos form, trackers) becomes `<CardTitle level={2}>…</CardTitle>`. All nine were `h2`, under a page `h1`, so the outline is the same. |
| `ConsoleFooter` has a `meta` snippet (#12). | The version leaves `footerLinks` and is rendered through `meta` as plain `v<version>`. The plain fallback footer (no platform address) shows it as a `<span>` too. The API reference link stays, since it is a real destination. |

## Scope

`web/package.json`, `web/package-lock.json`, `web/src/lib/locale.ts`, `web/src/routes/+layout.svelte`,
the four page files with card titles, and two render tests. No server change, route, `OF_*` key,
migration, Dockerfile or CI change. The lockfile is regenerated with npm 10 (what CI and the image
use), so it carries only the package's own entry and the root version that release-please had
already moved in `package.json`.

## Invariants impact

None. The bundle stays static and carries nothing about the deployment; no string is added or
removed, so the six catalogs are untouched; no polling or session change.

## Public interfaces and cost

No public interface changes. The console's visible change is colours and the footer version no
longer being a link.

## Testing approach

- `layout.render.test.ts`: in the shared footer and in the plain fallback footer, the version text is
  present and no link contains it.
- `o/[org]/page.render.test.ts`: the overview's card titles are `h2` elements (`Recent jobs`,
  `Repos`), and no heading contains another. Both fail against the 0.2.0 markup.
- The type change is covered by `npm run check`.
- A light/dark screenshot check of a few pages, including a form and a destructive action, kept out
  of the repo.

## Risks

- The new colours are the package's decision, reviewed there; tower only confirms they render.
- npm 11 locally rewrites `peer` flags across the lockfile; regenerating with npm 10 avoids that churn.
